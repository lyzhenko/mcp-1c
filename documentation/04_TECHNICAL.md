# Техническая документация

## Слои

```
presentation/   MCP-инструменты (@Tool), JSON-ответы, CLI, бенчмарк
business/       домен: Definition/Method/Type/Enum, ContextSearchService, PlatformStatusService
infrastructure/ hbk-парсер, PlatformLocator, PlatformCache, PlatformContextStorage, PlatformCatalog
```

`presentation` не знает, откуда взялась справка; `business` работает с неизменяемой моделью
`PlatformContextData`; `infrastructure` отвечает за файлы, кэш и поиск.

## Разбор справки

1. `PlatformLocator` находит `shcntx_<locale>.hbk` среди установленных платформ.
2. `PlatformContextLoader` проверяет кэш по пути, размеру, времени изменения, языку и версии схемы.
3. При промахе `PlatformContextReader` обходит оглавление `.hbk`, определяет страницы каталогов
   (глобальный контекст, типы, перечисления) и разбирает HTML страниц специализированными парсерами:
   методы (сигнатуры, параметры, возвращаемое значение, примеры, примечания), свойства, типы
   (методы/свойства/конструкторы), перечисления и их значения.
4. `Mapper` переводит модель hbk в домен, сохраняя все поля. Раньше сигнатуры и конструкторы
   терялись на этом шаге — теперь это закрыто тестами.
5. Результат пишется в кэш (`PlatformCache`, JSON, атомарная запись).

Незнакомый блок справки не обрушивает разбор: `UnknownBlocks.skip` пропускает его и один раз пишет
предупреждение в лог — новая версия платформы не делает сервер нерабочим.

## Фоновая загрузка

`PlatformContextStorage` запускает разбор в отдельном потоке из `@PostConstruct` (в stdio-режиме
MCP-сервер занимает основной поток раньше, чем успевают отработать `ApplicationRunner`).
Состояния: `idle → loading → ready|failed`. Модель публикуется через volatile-ссылку, чтение
не блокируется.

Инструменты вызывают `CatalogProvider.catalog()`, который ждёт готовности не дольше
`platform.wait-timeout-ms` (по умолчанию 25 с). Не дождался — ответ `platform_not_ready`, а не
многосекундное подвисание вызова. `status` не ждёт никогда.

## Поиск

`PlatformCatalog` строится один раз на загруженную модель: типы, глобальные методы и свойства,
перечисления, значения перечислений и члены типов (с владельцем). Поиск — линейный проход
с ранжированием, без поддерживаемых вручную индексов:

| Ранг | Совпадение |
|---|---|
| 0 | точное имя (включая «Тип.Член» и английское имя) |
| 1 | имя начинается с запроса |
| 2 | запрос входит в имя |
| 3 | точное английское имя |
| 4 | запрос входит в английское имя |
| 5 | запрос входит в описание (от 3 символов) |
| 6 | все слова запроса есть в имени или имени владельца |
| 7 | все слова запроса есть в описании |

Сортировка: ранг, затем длина имени, затем имя. При пустом результате — подсказки: сначала имена,
содержащие запрос, затем близкие по расстоянию Левенштейна (≤ 2), плюс список типов, у которых есть
элемент с таким именем. Ошибки в имени («СтрНайди») дают `suggestions`, а не пустой ответ.

Замер на 8.3.27: p50 — 6 мс, p95 — 22 мс на 90 запросах по каталогу из 1 739 типов и 16 521 члена.

## JSON-ответы и предел размера

`JsonResponseService` собирает ответы через Jackson:

- страницы: `total`, `returned`, `nextOffset`, `hasMore`;
- карточка: `kind`, `name`, `nameEn`, `description`, `signatures`, `parameters`;
- ошибка: `error.code`, `error.message`, `error.suggestions`, `error.memberOwners`.

Ответ ограничен `response-limit` (24 000 знаков). Если не влезает, страница уменьшается и отдаётся
`nextOffset`; если не влезает один элемент — длинные строки сокращаются, ставится
`"truncated": true` и подсказка сузить запрос. JSON всегда остаётся валидным.

Spring AI по умолчанию сериализует результат инструмента ещё раз, из-за чего готовая JSON-строка
превращалась в экранированную строку внутри строки. `RawJsonResultConverter` возвращает строку как
есть — агент видит объект, а не его JSON-представление.

## Кэш

`PlatformCache`:

- файл `platform-<locale>-<hash>.json` в каталоге пользователя;
- конверт хранит схему, путь, размер, время изменения, язык и саму модель;
- запись атомарная (временный файл + `ATOMIC_MOVE`), битый файл не роняет загрузку;
- схема поднимается при изменении модели или правил разбора (сейчас 2).

Замеры на 8.3.27 (`shcntx_ru.hbk`, 38,9 МБ): разбор — 2,1 с, сохранение — 0,55 с,
чтение — 0,35 с, файл кэша — 17 МБ.

## Выгрузка конфигурации

`DumpIndexer` строит SQLite-индекс в `<файл>.building` и подменяет готовый файл только после
успешной записи. Схема версионирована (`DumpIndex.SCHEMA_VERSION`, сейчас 5): при изменении таблиц
или правил разбора старый индекс пересобирается.

Таблицы: `meta`, `objects` (вид, имя, синоним, путь, комментарий), `fields` (реквизиты, измерения,
ресурсы, табличные части и их реквизиты, формы, команды, макеты, значения перечислений),
`modules` (путь, вид, строки, размер), `routines` (имя, вид, экспорт, параметры с признаком
значения по умолчанию, границы), `metadata_refs` (обращения к объектам из кода и запросов),
`entrypoints` и `entrypoint_sources` (формы, подписки, задания, HTTP/веб-сервисы).
Для поиска без учёта регистра рядом с именами лежат `*_lower`-колонки: SQLite `lower()` не работает
с кириллицей.

Разбор:

- метаданные — `MetadataXmlParser` (DOM) читает объектные `*.xml` глубины 1; свойства, синонимы,
  `ChildObjects`, табличные части с вложенными реквизитами; формы и макеты-ссылки индексируются
  по тексту;
- модули — все `.bsl`; владелец определяется по самому длинному каталогу объекта, вид модуля —
  по суффиксу пути (`Ext/ObjectModule.bsl`, `Forms/<F>/...`, `Commands/<C>/...`);
- BSL — `BslParser`: токенизатор и структурный проход находят процедуры, параметры (с `Знач`
  и значениями по умолчанию), локальные переменные, вызовы, `Возврат` и обращения к метаданным
  в коде и текстах запросов; вычисляются неиспользуемые параметры и переменные;
- точки входа — `EntryPointParser`: `Events/Event` в `Form.xml`, `EventSubscriptions`,
  `ScheduledJobs`, методы `HTTPServices`/`WebServices`;
- текст читается `DumpTextReader` (BOM UTF-8/UTF-16, откат на windows-1251, нормализация переводов
  строк).

`DumpStorage` открывает готовый индекс по пути выгрузки и схеме или строит новый в фоне;
`status` показывает фазу (`метаданные`/`модули`/`формы`), прогресс и итоги. `dumpGrep` берёт список
модулей из индекса: обход 65 000 файлов выгрузки съедал бы весь бюджет поиска.

`dumpCheck` работает поверх `BslParser`: проверяет число аргументов у своих процедур, методов общих
модулей (по индексу) и глобальных методов платформы (по справке), отсутствующие объекты метаданных,
неиспользуемые переменные, функцию без `Возврат` и дубли процедур. Проверки консервативные:
неизвестная процедура — предупреждение, потому что разбор не является компилятором.

Замер на УНФ (6,1 ГБ, 65 048 файлов): индекс 158 МБ, сборка 28,1 с, 15 578 объектов,
66 746 полей, 14 737 модулей, 285 135 процедур, 52 370 обработчиков форм, 454 подписки, 189 заданий;
grep — 30 мс на 6 файлах; `dumpCheck` модуля в 11 081 строку — 0 ошибок и 7 предупреждений.

## Ограничения и что дальше

- Разбирается только синтакс-помощник; `shlang_*.hbk` и `shquery_*.hbk` не индексируются.
- Модель и индекс — снимки; после обновления платформы или выгрузки нужен перезапуск/`dumpReload`.
- Графа вызовов (`node`/`neighbors`) и вывода типов пока нет: `dumpCheck` использует структурный
  разбор, поэтому проверки консервативные, а «кто вызывает» без графа не отвечается.
- Расширения конфигурации не накладываются на базу: индексируется один каталог выгрузки.
